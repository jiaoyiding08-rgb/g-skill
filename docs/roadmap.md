# 后续开发顺序

## P0 · 首轮真实试用

先使用现有六个 Skill，不扩展名字。完成十个匿名真实案例的基线和 G 对比，记录输入、输出、评审和用户实际下一步。接受失败和不确定结论。验收依据是可复现记录，无证据不宣称提升。

## P1 · 可核验的内容与结果

设计独立人工审核回执，再接一个只读外部状态源。明确核验者、版本、时间、撤销、用户身份、订单/发布状态范围和审计。不得让模型凭截图代签 E2/E3。完成身份与多用户隔离后才讨论服务化。

## P2 · Review 和 Repeat 的实际作用

持续收集经过同意的独立任务，记录方法使用前后条件和反例。先做人工/半自动分类，验证 episode 去重、同目标不同载体、相似词不同目标。只有模板在新实例里通过，才进入 Skill 或自动化候选。

目前存储支持候选规则和簇，自动检索规则、语义聚类、流程瓶颈计算和规则有效性统计仍待实现。

## P3 · Lab 的完整工程实现

固定模型与供应商兼容性，补全实际 eval_runs/skill_versions 写入和报表。将留出集与开发过程隔离。保存候选文件哈希、差异、成本、模型输出、人工评审、回退快照。先人工审批，后小范围 Canary。最后再做可靠的发布与回退工具。

DSPy/GEPA 放到评估程序可靠之后。优化器只得到开发材料，不能看到真正留出答案。每轮规定预算和停止条件。连续无改善就停止。

## P4 · 用户授权的观察和操作

按实际需求逐个评估 Git、日历、文件、浏览器或桌面入口。先只读，再讨论写入。持续观察不是默认开启项。自动化需要可撤销授权、明确效果核验、异常停止和独立结果确认。

G Index、现金激励、社群排名和支付另立项目。本次不设计其规则，不把私人复盘直接变成公开分数。
