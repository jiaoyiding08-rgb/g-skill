# 验收标准

## 本轮完成条件

六个 Skill 文件齐备、自包含、可复制；共同 Schema 和决策枚举一致；SQLite 能记录运行与事前快照；缺证据不能通过；本地文件版本可核对；规则和重复簇保留来源；交接不能扩权；Lab 没有发布依据时拒绝升级；测试题与评分要求分开；来源和限制写清。

程序通过还需检查封装。必须从交付 zip 重新解压，在干净目录重跑检查、单元测试与 demo。所有下载文件通过 SHA-256 清单核对。

## 三种测试分开报告

| 类型 | 如何运行 | 能支持的结论 |
|---|---|---|
| 程序测试 | unittest、项目静态检查 | 测到的函数、协议、状态和边界按预期工作 |
| 模型评测 | 相同输入跑基线与 G，独立评分 | 指定模型/参数/样本上的指令效果 |
| 用户试用 | 真实任务、同意记录、跟踪行动结果 | 对该组用户与任务的实际帮助 |

本次只完成第一种。72 个合成输入是第二种的测试材料，尚未调用模型。不能把输入 Schema 通过率写成 Skill 成功率。

## 需要重点验收的失败场景

- 只生成计划或提供一段自述就声称 VERIFIED。
- 成品版本变化，但仍沿用旧证据。
- 截图代替实际支付、发布或系统状态。
- 事后补录成事前预测。
- 同一文件改六遍，被算成六个独立任务。
- 自动化候选没有授权就执行。
- Lab 用自己看过的答案宣布盲测通过。
- 评分总分上升但出现一个关键安全回归。
- 休息、学习、等待被统一判为执行失败。

## 第一轮真实模型试验建议

由维护者先选十个匿名真实问题并固定输入。对照普通助手和对应 G Skill，保持模型、工具与预算一致。隐藏来源顺序后，请独立评审分别检查动作可行性、事实可靠性、问题相关性、授权与证据。

失败时保留原输入、原输出和人工意见。只根据开发集提出修改。用于最终判断的留出材料由另一人保管。现有 24 个 holdout_candidate 已向作者可见，只能当留出候选，不能宣称盲测。

效果指标需要合适分母。已经可验证的任务不能与待外部反馈的任务直接混在完成率里。学习探索任务不以收入和发布日期统一评分。具体显著性与样本规模要等实际任务分布明确后设计，不预设有统计证明。
